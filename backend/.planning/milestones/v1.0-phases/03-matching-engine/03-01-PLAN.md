# Plan 01: Core Matching Service & Transaction Logic

<objective>
Implement the matching algorithm component (`MatchEngineService`) that groups waiting queue entries by `region_id`, `sport_id`, and `skill_level`. It will use database row locking (`FOR UPDATE SKIP LOCKED`) to grab records concurrently, finalize a `Match` and `MatchPlayers`, and hook into `BookingService` to secure a ground.
</objective>

<requirements>
- MATCH-01
- MATCH-02
- MATCH-03
- MATCH-04
</requirements>

<tasks>
  <task>
    <description>Add batch locking query to QueueEntryRepository</description>
    <read_first>
      - modules/matchmaking/repository/queue_entry_repository.py
    </read_first>
    <action>
      In `queue_entry_repository.py`, add `find_and_lock_compatible_pair(region_id: int, sport_id: int, skill_level: str, session: Session) -> list[QueueEntry]`:
      1. Query `QueueEntry` where `status == 'WAITING'`, region/sport/skill match the params.
      2. Order by `created_at` ASC (Strict FIFO matching priority per D-04).
      3. Use SQLAlchemy's `with_for_update(skip_locked=True)` to prevent concurrency deadlocks (MATCH-04).
      4. Limit to 2 records and return them.
    </action>
    <acceptance_criteria>
      - `queue_entry_repository.py` contains `find_and_lock_compatible_pair` method.
      - The method includes `.with_for_update(skip_locked=True)`.
      - The method includes `.order_by(QueueEntry.created_at.asc())`.
      - The method includes `.limit(2)`.
    </acceptance_criteria>
  </task>

  <task>
    <description>Implement MatchEngineService grouping logic</description>
    <read_first>
      - modules/matchmaking/repository/queue_entry_repository.py
      - modules/match/model/match_model.py
      - modules/match/service/match_engine_service.py (create this if missing)
    </read_first>
    <action>
      Create `modules/match/service/match_engine_service.py` with class `MatchEngineService`.
      Implement `process_matching_cycle()`:
      1. Find all distinct `(region_id, sport_id, skill_level)` groups that have `>= 2` WAITING entries using a group_by count query (add `get_matchable_groups()` to the repo). D-02 exact match strictness.
      2. For each matchable group, start a new database transaction.
      3. Call `find_and_lock_compatible_pair` inside the transaction.
      4. If exactly 2 entries are locked:
         a) Pick the oldest as `creator_id`.
         b) Create a pending `Match` record with `status='MATCHED'` and mapped fields.
         c) Create two `MatchPlayer` records for the queued users.
         d) Mark both `QueueEntry` records as `status='MATCHED'`.
         e) Call `_secure_booking_for_match(match, creator_id)`.
      5. Commit the transaction if successful, rollback if fails.
    </action>
    <acceptance_criteria>
      - `match_engine_service.py` contains class `MatchEngineService`.
      - Contains method `process_matching_cycle`.
      - Creates a new `Match` and `MatchPlayer` instances inside a `session.commit()` block.
    </acceptance_criteria>
  </task>

  <task>
    <description>Integrate BookingService to auto-secure ground</description>
    <read_first>
      - modules/match/service/match_engine_service.py
      - modules/booking/service/booking_service.py
    </read_first>
    <action>
      In `MatchEngineService._secure_booking_for_match`:
      1. Find the earliest available `timeslot_id` for today in the `region_id`.
      2. Grab a default `cart_type_id` (e.g. first available 'turf' or general type for the region).
      3. Construct booking payload: `user_id` (creator), `region_id`, `cart_type_id`, `timeslot_id`.
      4. Call `booking_service.create_booking(payload)`.
      5. If booking fails (e.g., ValueError regarding capacity): D-03 states "Keep matched users in the WAITING queue implicitly until a ground opens up".
         -> ROLLBACK the transaction. The inner try-except should catch `ValueError` from booking service, rollback the session so the `QueueEntry` rows stay `WAITING`, and log the incapacity.
      6. If booking succeeds, update `Match.cart_type_id` and maybe a reference to the pending booking (if schema supports it). Currently `Match` has `cart_type_id` and `cart_id`. We only have `cart_type_id` until booking confirms.
    </action>
    <acceptance_criteria>
      - `match_engine_service.py` contains `_secure_booking_for_match` method.
      - Catch block specifically handles booking setup failures by rolling back to keep users in `WAITING`.
      - `booking_service.create_booking` is invoked with correct payload structure.
    </acceptance_criteria>
  </task>
</tasks>

<must_haves>
- Uses `SKIP LOCKED` row-level locks to prevent overlapping queue consumers assigning the same users simultaneously.
- Exact match strictness (BEGINNER only matches with BEGINNER).
- Strict FIFO by `created_at`.
- Failed bookings rollback gracefully returning users to WAITING status.
</must_haves>
